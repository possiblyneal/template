# Repo Builder

## Purpose

Develops the `/repo-builder` skill, which builds a repository from the payload at `apps/github-repository-template/src/base-repo/` and carries later template deltas into repositories already generated from it. The skill is this repository's product, so it lives under `apps/` like any other unit; a clone links it into place rather than holding a second copy.

## Ownership

- `src/SKILL.md` — the entry point, and the only file Claude Code reads to decide the skill applies.
- `src/references/` — the flows the entry point routes to: `lifecycle.md` first, then `generate.md`, `update.md`, `adopt.md`, `retrofit.md`, `wayfinding.md`, `addon-adoption.md`, and `reporting.md` at the end of any of them. `retrofit.md` is an index: it lists the `lifecycle.md` sections a retrofit reads up front instead of the whole file, and the step that reads each of the rest, states the records convention once, and links one file per step, `retrofit-step-1-preflight.md` through `retrofit-step-9-publish.md`, each read when the flow reaches it. `retrofit-unmet-bar.md` is read from step 7 only when the bar is unmet, and `retrofit-report.md` once the flow ends or stops. The reasoning behind the flow's shape is `docs/adrs/0005-stage-a-retrofit-locally-and-write-the-host-last.md`, which step files link rather than restate. A lifecycle rule a retrofit newly depends on goes on that list or behind a link at the step that needs it, or the flow never reads it. `choosing_a_language.md` is the method wayfinding is a short path through.
- `src/scripts/preflight.py` — validates and describes a flow's inputs before it acts. Retrofit shares the git helpers and the addon manifest reader, and none of the record ones: every check in `load_provenance` reads a `.repo-template.json` a retrofit has not written yet.
- `src/scripts/retrofit.py` — runs a retrofit's fixed steps and reports each as JSON: `proofs`, `normalize`, `facts`, `autofix`, `hooks`, `sweep`, `hosted read` and `hosted apply`, plus `report` and `pr-body`, which render the final report and the pull-request body from the records the others wrote. It writes where `preflight.py` is read-only by contract, which is why it is a second file rather than more subcommands there; it imports `preflight.py`'s git helpers rather than copying them.
- `src/scripts/tests/` — the pytest suite over `preflight.py`, `retrofit.py` and `src/evals/verify_fixture.py`'s retrofit grading, plus two checks that are not about this unit's code: `test_addon_adoption.py`, on the template payload, and `test_reference_assertions.py`, on whether `src/references/` still describes a payload that exists and whether every payload path is reached by an ownership rule.
- `src/evals/` — `evals.json` and the fixture helpers the skill-eval tooling runs it against. `verify_fixture.py` grades a retrofit fixture (`retrofit`, `retrofit-red`) against the candidate worktree it finds on the destination clone's `retrofit/<first 12 of the target commit>` branch; it grades the candidate and the clone, not the chat report, which has no fixed path.
- `scripts/install` — creates the link described below.

## Local Contracts

**The link is the install.** `apps/repo-builder/scripts/install` creates `.claude/skills/repo-builder` as a symlink to `../../apps/repo-builder/src`, and `.gitignore` holds it out of the tree. It is a deployment artifact of this unit, not repository content: committing it, or committing a copy of the skill beside it, puts the skill at two paths and the second one goes stale. Every clone runs the install once.

**The link targets `src/`, not the unit root.** A skill directory is `SKILL.md` plus the paths beside it; `.unit.json` and this file are this repository's bookkeeping and have no meaning to the skill.

**The skill runs from this repository.** Its paths are repository-root-relative — `apps/github-repository-template/src/base-repo`, `src/addon-adoption.json` — and the destination is an argument rather than the working directory. A session that invokes it from somewhere else resolves those paths against the wrong tree. A generate's candidate is repository-root-relative too, under the gitignored `tmp/`, so it cannot be committed here and materializing a whole tree needs no approval for a path outside the repository. `references/generate.md` step 3 names it and `SKILL.md` repeats it for routing; a third copy of the path is one more than can be kept in step.

**`ships.kind` is `none` because the vocabulary has no word for this.** The three kinds are `executable`, `quadlet`, and `none`, and a symlinked skill is none of them. Adding a fourth means editing `scripts/structure`, which is mirrored into the payload, so every generated repository would gain a kind it has no unit to use; `docs/adrs/0001-declare-unit-delivery-as-two-facts.md` gates the declaration's shape. `none` here reads as "nothing this repository's packaging adapters build", which is accurate — `scripts/install` is what delivers it.

**The retrofit fixture copies the payload's real layout audit.** `src/evals/setup_fixture.py` reads `scripts/structure` and `scripts/libs/result.sh` out of `apps/github-repository-template/src/base-repo/` rather than writing a stand-in, because a retrofit is scored on its destination's own check surface and a hand-written audit would prove nothing about the rules this template actually enforces. Moving either payload path breaks the two retrofit scenarios.

**Two root-level checks name paths inside this unit**, and moving a file here breaks them silently rather than loudly: the `addon-adoption` pre-commit hook's `entry`, and `testpaths` in the root `pyproject.toml`. The root `pyproject.toml` exists for this unit's Python; it is root-only and never mirrored into the payload.

**A retrofit's records sit at one prefix.** `<records>` is `tmp/<repository-name>.<first 12 of the payload commit>` under this repository. Every `retrofit.py` subcommand requires `--records <records>` and writes its JSON to `<records>.<name>.json`, unlinking the earlier one first so a failed run leaves no stale record — `hosted apply` alone reads it before the unlink and keeps the writes a later call does not approve, unless a sweep has run since it was written; the write log `hosted apply` keeps and `sweep` removes is `<records>.writes.json`, derived rather than passed; `report` and `pr-body` take no per-record flags and read them by name, so a missing record means its subcommand did not run. A new subcommand whose output the report or the body needs writes a record under this convention rather than adding a flag to either renderer. `references/retrofit.md` states the convention for the flow; this is its home for the code.

## Work Guidance

`test_addon_adoption.py` and `test_reference_assertions.py` are stdlib-only, and each file says why: both run under pytest and standalone from a pre-commit hook that resolves no dependencies. A pytest-only idiom added later passes the first and breaks the second.

`test_reference_assertions.py` checks only mechanical claims — a destination path a reference names exists in the payload or in `repository-addons/`, a decision record it cites exists under `docs/adrs/`, and a Markdown heading it quotes exists in some payload file or in `src/references/` itself. The heading set spans both trees because a quoted heading is one of two claims: payload content a flow acts on, or an address one reference cites in another, which is what `generate.md`'s `### Step N` headings are for. Whether a sentence is right about a file it names is not decidable there, so widening it means finding another claim a script can settle, not loosening these three.

A fourth claim was added that way: every path the payload ships is reached by an ownership rule, checked against this repository's `.repo-template.json` and against the manifest example in `lifecycle.md`. It reads two manifests rather than the references, and it belongs here because the claim it settles is one the references make — an unmatched path is product-owned, so a payload path no rule reaches sits outside every update with nothing naming it. It asserts reachability of each list separately rather than agreement between them, because the two describe different repositories and are free to diverge: this repository's manifest is the payload's shape plus its own merges. Each is kept complete on its own, which is what makes a rule added to the payload a rule added to both. `reaches()` is a hand-copy of `preflight.py`'s `path_matches` for the two shapes the manifests use, kept rather than imported for the stdlib-only reason above; it is strictly the narrower of the two, so it can only false-alarm.

Every git command `test_preflight.py` writes by hand goes through its own `git` or `git_output` helper, never `subprocess.run` direct. The helper supplies a `-c user.name`/`-c user.email` identity on every call, because a hand commit is the only kind that falls back to ambient git config and a CI runner has none — its gecos field is empty, so git fails with "empty ident name" where a developer machine silently succeeds. A new call site that bypasses the helper passes locally and fails in CI. Fixture commits are exempt: `src/evals/setup_fixture.py` carries its own `GIT_ENV`. `test_retrofit.py` imports those two helpers from `test_preflight.py` rather than holding a copy, so the rule has one home. A subcommand that commits itself, as `hooks` does in its throwaway worktree, gets the same identity through `GIT_AUTHOR_*`/`GIT_COMMITTER_*` in the environment the test runs it under, and an isolated `GIT_CONFIG_GLOBAL` so the machine's own global hooks never reach the run. `HooksTests` run the payload's real hooks and skip, naming why, where pre-commit cannot build their environments. They copy the payload over the fixture rather than building a retrofit's real layout, and set a prior `core.hooksPath` per case through that isolated config — none, global, or local — since which directory git was running decides what gets chained. The host is the one thing the suite stands in for: `stub_gh` in `test_retrofit.py` puts a `gh` first on `PATH` that replays recorded responses and logs every call, so a test asserts both what the host answered and which writes were sent.

Editing under this unit's `src/` does not prompt — `.claude/settings.json` asks only for `apps/github-repository-template/src/**`, where the prompt's question, payload or root, is a real one.

## Verification

- `uv run pytest` — the suite, bounded here by the root `testpaths`. Runs inside `scripts/check` as the Python test capability.
- `pre-commit run addon-adoption --all-files` — the payload manifest check, at this unit's path. Runs on every commit.
- `pre-commit run reference-assertions --all-files` — the references-against-payload check. Runs on every commit.
- `src/evals/` is run by the skill-eval tooling against the fixtures its helpers build. It is not part of `scripts/check`: an eval invokes the skill, which is a model run rather than a check.
